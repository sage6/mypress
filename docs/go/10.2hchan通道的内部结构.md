## 10.2 hchan:通道的内部结构

10.1从CSP的角度交代了通道在语言里的位置：它是显式的消息信道，把通信与同步合二为一。这一节把它拆分开来看。一个channel在运行时就是一个名为hchan的结构体，它的全部秘密不过是一把锁，一圈环形缓冲，
外加两条等待队列。结构虽小，每个字段的存在都对应一处设计上的考量，读懂这几样东西，后面收发与select的全部逻辑（10.3-10.6内存模型与无锁演进）就只是在这张图上搬运数据，挂起与唤醒goroutine。

沿用本书讲运行时的数据结构的惯例，下位给出的结构体是裁剪后的速写，只留于设计相关的字段，并在注释里面说明它为何存在。完整定义可对照runtime/chan.go与runtime/runtime2.go。

### 10.2.1 三条不变式：先看为什么

在逐字段拆解之前，先抄下chan.go开头那段注视下的三条不变公式，它们是整套结构的设计意图，比任何字段说明更能说清楚为何如此：

- c.sendq与c.recvq至少已有一个为空（唯一例外是：一个无缓冲channel上，某个goroutine用select同时在收和发量测挂着）；
- 对缓冲channel，c.qcount > 0蕴含c.recvq为空；
- 对缓冲channel,c.qcount < c.dataqsiz蕴含c.sendq为空。

这三条用日常语言说就是一句话：缓存里还有货，就不该有接收方在干等；缓存还有空位，就不该有发送方在干等。一旦缓存与干等的人同时存在，说明可以直接成交却没有成交，那就是bug。整个收发实现（10.3）所做
的，正是时刻维持这三条：能直接成交就直接成交，是在成交不了才把自己挂进等待队列。带着这个意图会看下面这段文字，就不再是枯燥的清单。

### 10.2.2 hchan的速写

```go
// hchan:一个channel的运行时表示（速写）
type hchan struct {
    qcount uint // 缓存中现有元素个数
    dataqsiz uint // 环形缓冲的容量（make的第二个参数）
    buf unsafe.Pointer // 指向一段可存dataqsiz个元素的连续数组
    elemsize uint16 // 单个元素的大小（由元素类型推出，缓存于此免去反复查表）
    closed uint32   // 是否已close
    elemtype *_type // 元素类型：拷贝元素，写屏障，给buf标注GC信息都要用它
    sendx uint // 环形缓存的写游标(下一个待写入的槽)
    recvx uint // 环形缓存的读游标（下一个待读出的槽）
    recvq waitq // 阻塞的接受放队列(<-ch)
    sendq waitq // 阻塞的发送方队列(ch<-)

    lock mutex // 一把锁,守护以上所有字段
}
```

字段大概分为三组。qcount, datasiz, buf, sendx, recvx五个合起来描述那圈环形缓存（10.2.3）;recvq，sendq是两条等待队列（10.2.4）;closed记录关闭状态，selemsize与elemtype是为搬运元素
备下的元数据。其中datasiz在创建之后不再写入，因此运行时可以无锁读它来判断channel是否有缓存（full等辅助函数依赖这一点）。至于elemtype,它不只用于按值拷贝元素和触发写屏障，还在创建时候被交给
分配器，用来给buf标注这段内存里面那些位置是指针，这一点到10.2.5会再回来。(go1.26的hchan还有timer与bubble两个字段，分别服务于time定时器于testing/synctext，与本节的主线无关，速写中省去)。

### 10.2.3 环形缓存：sendx与recvx是头尾游标

缓冲channel的那段缓存是一个环形队列（ring buffer）。buf指向一段能放dataqsiz个元素的连续内存，sendx与recvx是两个游标：发送方把元素写到sendx处再让它前进，接收方从recvx处读出再让它前进，二者
各自走到末尾就回绕到0。qcount记录当前存量，于是队列满就是qcount == dataqsiz，队列空就是qcount == 0。定位第i个槽不过是一次指针算术：

```go
// chanbuf(c, i):取buf中第i个槽的地址
func chanbuf(c *chan, i uint) unsafe.Pointer {
    return add(c.buf, uintptr(i)*uintptr(c.elemsize))
}
```

为什么使用环形而非线形队列？因为channel的收发室严格的FIFO:先发的先收。线性数组在头部出对后留下空洞。要么搬运元素，要么浪费空间；环形队列让读写两端个字环绕，出对入队都是O(1)的游标自增加回绕，
不再搬一个字节。下图是一个容量为6，已存3个元素的channel，recvx指向最早入队，即下一个被读走的元素,sendx指向下一个空位：

发送时候写入sendx,`sendx = （sendx + 1）% dataqsiz, qcount++;`接收时候读出recvx,`recvx = (recvx+1) % dataqsize,qcount--`。运行时不再取模，而是写成
`if sendx == dataqsiz { sendx = 0}`,省一次除法。回扣10.2.1的不变式：主要qcount在0与dataqsiz之间，就说明缓存即没有满也没空，收发都能就地完成，两条等待队列此刻必定是空的。

### 10.2.4 等待队列：sudog的FIFO链表

当缓存帮不上忙，比如像满了的channel发送，从空的channel接收，或者channel根本没有缓存，当前goroutine就得挂起，等对面来人。它挂到哪里？挂进recvq或者send。这两条队列的类型是waitq，一个朴素
的双向链表，记着头和尾：

```go
type waitq struct {
    first *sudog // 队头：最早挂起，最先被唤醒
    last *sudog // 队尾: 最新挂起
}
```

链表的节点是sudog。理解channel，sudog时绕不开的一个环：它代表一个正阻塞的channel的goroutine，连同它收发的那个元素槽。裁剪后的速写：

```go
// sudog：一个挂在channel上的goroutine + 它要收发的元素（速写）
type sudog struct {
    g *g // 被挂起的那个goroutine

    next *sudog // 在waitq中的后继
    prev *sudog // 在waitq中的前驱

    elem maybeTraceablePtr // 待收发元素的地址，可能直接指向g自己的栈

    isSelect bool // 改g是否正参与一次select（唤醒时候需要CAS抢占）
    success bool // 唤醒原因：true=成功收发，false=channel被close
    c maybeTraceableChan // 它阻塞在哪个channel上
}
```

为什么不直接把`*g`串进队列，而要套一层sudog?因为一个goroutine阻塞在一个channel上不是一对一的：同一个goroutine可以在一条select语句里面同时挂多个channel上，同一个channel也排着多个
goroutine。sudog正是goroutine,channel这一次等待的载体，一个goroutine因此可能同时拥有多个sudog。sudog不为channel独有，sync包的信号量（11.x）也用同一种结构排队，上面isSelect,
sucess之外的若干字段就是为信号量准备的，速写已略去。运行时用一个每P的缓存来复用sudog，省去频繁分配。

elem字段值得专门点出：它指向这次要发送或者接收的元素。而这块内存往往就在改goroutine自己的栈上。这正是channel一项关键优化的基础：发送方遇到一个已在recvq里面干等的接收方时，可以把数据直接
拷贝进接收方栈上的elem,跳过环形缓存这道中转（10.3详述）。这也解释了为何sudog上这些字段要由channel的锁保护：唤醒一方，写它的栈，都得在持锁时进行。

队列本身时严格的FIFO。入队挂到队尾，出队从头部摘下：

```go
func (q *waitq) enqueue(sgp *sudog) {
    sqp.next = nil
    x := q.last
    if x == nil { // 空队列
        sgp.prev = nil
        q.first = sgp
        q.last = sgp
        return
    }
    sgp.prev = x // 接到队尾
    x.next = sgp
    q.last = sgp
}

func (q *waitq) dequeue() *sudog {
    // 从队头摘： select唤醒竞争下需要跳过已被别处唤醒的节点，此处从略
    sgp := q.first
    // ...更新first/last,返回sgp
    return sgp
}
```

先挂起的先唤醒，这保证了通道收发的公平：没有哪个等待着会被无限期插队。10.2.1那条至少一个队列为空的不变式在这里也有了直观解释：若缓存有空位或者有货，新来的接收方当场就成交了，根本不会走到入队这一
步，因此两队列不会同时排空（select双挂的特例除外）。

### 10.2.5 makechan: 一次分配，noscan优化

make(chan T, n)被编译器翻译makechan(t, n)。它的本职工作是算出缓存所需要内存，向堆申请，填好元信息。channel总是分配在堆上，由GC负责回收，这也是为什么不显式close也不会泄漏内存（关闭与回收
时两回事）。值得玩味的是它按照元素类型分了三种分配策略：

```go
func makechan(t *chantype, size int) *hchan {
    elem := t.Elem
    mem, overflow := math.MulUintptr(elem.Size_, uintptr(size)) // 缓存总字节数
    if overflow || mem > maxAlloc-hchanSize || size < 0 {
        panic(plainError("makechan: size out of rang"))
    }

    var c *hchan
    switch {
    case mem == 0:
        // 无缓存（size == 0),或者元素零大小（如sturct{}):根本不需要buf
        c = (*hchan)(mallocgc(hchanSize, nil, true))
        c.buf = c.raceaddr()
    case !elem.Pointers():
        // 元素不含指针，hchan与buf一次性分配在同一块内存里面，且整块noscan
        c = (*hchan)(mallocgc(hchanSize+mem,nil, true))
        c.buf = add(unsafe.Pointer(c), hchanSize)
    default:
        // 元素含指针：buf必须单独分配，并带上elemtype让GC能扫描它
        c = new(hchan)
        c.buf = mallocgc(mem, elem, true)
    }

    c.elemsize = uint16(elem.Size_)
    c.elemtype = elem
    c.dataqsiz = uint(size)
    lockInit(&c.lock, lockrankHchan)
    return c
}
```

三条分支的分界，是GC要不要扫描这段缓存：

- mem == 0同时罩住了两种情形：无缓冲channel(size == 0)，以及元素是零大小类型（chan struct{},常用作纯信号）。两者都不需要buf，只分配一个hchan,buf指向一个仅供竞争检测器（-race）当同步
  地址用的占位。
- ！elem.Pointers()，元素里面没有指针：hchan和buf在一次mallocgc调用里面一并分出，buf紧贴hchan之后（c.buf = add(c, hchanSize)）。一次分配省去一次调用，更关键的是传入的类型是nil,
  整块内存被标为noscan,GC扫描直接跳过这段缓存，对元素是int,byte之类的高频channel是实打实的开销节省。
- 元素含指针：buf只能单独分配，且分配时必须把elemtype传进去。原因正是于上一条的反面，GC必须扫描这段缓存里面的指针，否则缓存中尚未取走的元素所引用的对象会被误回收。把elemtype交给分配器，就是把
  这块内存等级好哪些自是指针的位图。此时hchan与buf分属两块内存，不能合并。

可见makechan不是简单地分配一段内存，它和GC是协同的：能noscan就noscan，必须扫描就如实标注。这与12内存分配里面分配器对含指针/不含指针对象的区分是同一种思路，channel只是它的一个使用者。

### 10.2.6 一把锁，与它撑起的同步语义

hchan末尾哪个lock mutex时整个结构的同步基石。它守护的不只是hchan自身的所有字段，还包括挂在这个channel的那些sudog里面的若干字段，源码注释为此特意标明。收，发，关闭，select，凡是要动这些
状态的操作，第一步都是lock(&c.lock)，最后一步是unlock。正因为有这把锁串起全程，channel的一次发送与对应接收直接才能建立内存模型中的发生序（happens-before,11.9），channel由此既是通信
手段，也是同步手段。

把这把锁业带来了一条微妙的纪律：持有c.lock时候不得去改变另一个goroutine状态（尤其不得goready唤醒它）。原因是唤醒可能触发栈收缩。而栈收缩又回去强这把锁，二者交叉就会死锁。收发实现里面那些
先在持锁摘下sudog，解锁后goready的别捏写法根源就在这里（10.6内存模型与无锁演进展开）。

用一把锁守护整个channel，是一个有意思的取舍：实现简单，正确性容易论证，代价是同一个channel上并发收发会在这把锁上串行化。社区与运行时作者早就探讨过无锁channel：Dmitry Vyukov 2014年前后
提交过一份无锁channel的实验设计，最终因为复杂度增长远超它带来的收益而未被合并。直到今天，标准channel仍是这把朴素的锁加环形缓存的组合。把这把锁看明白，收发与select的全部细节（10.3-10.6
内存模型与无锁演进）就只是在持锁的临界区里面，按照10.2.1的不变式搬数据，挂起与唤醒而已。

它省下了什么？对照经缓存的笨办法：发送方先把值拷进buf(进)，接收方唤醒来后再从buf拷贝自己的变量（出）,一进一出两次拷贝，外加缓存槽的占位与回收。direct handoff把两次合成一次跨栈memmove。代价
是它必须在持有channel锁，且接收方处于\_Gwaiting(9.3)尚未运行时进行，正因为接收方此刻没有在跑，没有用户态代码会与这次跨栈写入竞争，直接写到别人的栈才是安全的。这里的typeBitsBulkBarrier是
必须的：跨栈写入含有指针的值，要让垃圾回收器看见这次指针的转移。

一个容易忽略的次序：send先unlockf()解锁，再goready唤醒接收方。数据再解锁前就已拷贝完毕，因此被唤醒的接收方一睁眼，值就已经躺在它的变量里面，它无需再碰channel，直接返回即可。注意这里只是把
接收方标记为可运行并放回运行队列（9.4），并不立即切换过去。
