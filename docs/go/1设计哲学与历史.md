# 1 设计哲学与历史

## 1.1 编程语言的发展

要理解Go为何长成今天这样，为何如此克制，如此偏执于速度，如此看重并发，得先看它诞生时面对的
是怎样一片语言版图，以及它想替谁解决怎样的痛。

### 1.1.1 语言演化的几条主线

1. 1950年代末，Fortran让科学计算摆脱汇编，Lisp带来高阶函数与自动内存管理。
2. 1960年代Algol确定了结构化的块与语法；1970年代C与Unix一同诞生，给系统程序员一种贴近及其又不必要写汇编的语言。
3. 1980，90年代C++与Java把面向对象推向主流，前者零成本，后者可移植与托管；同期Python,Perl等脚本语言以开发效率见长。
4. 2000年代以后，Go与Rust代表了重新审视系统编程的两种回答，一个赌简单与并发，一个赌编译期的内存安全。

每一步背后，是在几个维度做了一组特定取舍。

- 抽象层级：从汇编的直接操纵机器，到C的过程抽象，到C++/Java的对象抽象，到函数式的高阶抽象。层级越高，表达越凝，离机器越远，对性能和可预测性的掌控也越弱。
- 内存安全：从C手工malloc/free，到带来及回收的托管语言，再到Rust的所有权。
- 并发编程：从手工线程加锁，到CSP/Actor等更高级的消息传递，到sync/await的无栈协程。
- 类型系统：在静态强类型的安全与动态类型的灵活之间反复摆动；又在名义类型与结构化类型直接各有选择。
- 工程性：编译速度，构建模型，工具链，依赖管理。这一维度被语言设计者轻视，却恰恰是大规模软件协作的命脉，也是Go着力最猛的地方。

# 1.1.2 设计者血脉

Go的基因：**Unix极简主义**（小，正交，组合），一条二十年的并发语言谱系（CSP与channel),一线的编译器与运行时工程经验（极快的编译，厚重的运行时）。

### 1.1.3 Go诞生时不满

- 编译慢到拖垮速度。
- 依赖管理混乱
- 并发难写又危险
- 语言过于庞杂

### 1.1.4 一种【少即是多】的回应

Go的回应，是一种可以的克制。它选择了：编译为本地机器码，带垃圾回收，静态类型；一套极简的语法（仅25个关键字，少到能一口气背完）；以CSP为蓝本的并发；
以组合而非继承为骨架的类型系统；以及对工具链与构建速度的极度重视。

它有可以不要的东西，和他要的东西同样醒目，且每一项不要都对应着上面某个痛或者某条价值：

- 很长时间没有泛型。
- 没有异常，错误是普通的值，显式返回，显式处理，拒绝隐式的控制流跳转。
- 没有继承，用接口与组合替代，避免类层级的脆弱与纠缠。
- 没有运算符重载，没有隐式类型转换，拒绝看一行代码猜不出它在干什么的魔法。

### 1.1.5 复杂度必须挣得它的位置

理解了Go诞生时候的这些不满于回应，本书后面对每一处的剖析，为什么调度器是协作加信号抢占，为社么内存模型只给顺序一致原子，为什么GC死磕低延迟，就都有
一个共同的坐标原点：它们都是简单，工程友好，为真实的大规模软件协作服务这组价值。

## 1.2 Go语言综述

### 1.2.1 三层视角与厚重的运行时

理解Go,可以分为三层来看，本书也大致按照这三层加上历史铺陈来组织。

**语言层**，你直接书写的东西：语法，类型系统，并发原语，错误处理。它可以小而正交，25个关键字就是全部。
**运行时层**, 与你的程序一起被编译进同一个二进制，在背后默默支撑小操作系统；goroutine调度器，内存分配器，垃圾回收器，栈管理。这是Go最厚重，也是最
值得剖析的地方。
**工具链层**,把源码变成可运行，可诊断，可维护的程序的机器：编译器，链接器，模块系统，测试与可观测工具。

Go的一个鲜明的特征，就是它的运行时异常厚重，一门C程序几乎不带运行时，一门Java程序把运行时放进一个独立的虚拟机，Go走的是第三条路线，它把调度，垃圾回收，
栈管理这些本属于操作系统范畴的复杂度，接管与你的代码一同编译，一同链接的运行时里面，换取上层的简洁：一个go关键字就能并发执行，自动内存管理，可以在任意
深度阻塞的goroutine.代价时二进制更大，运行时本身的复杂度可观，但是收益时部署极简，并发与内存管理对用户透明。

### 1.2.2 几个与众不同的设计

Go的气质主要集中在几个和直流语言不一样的决定上。下

- **并发是语言的一等公民(CSP)**。启动一个并发执行只需要go,协调用channel,不必碰线程库与锁。

```
ch := make(chan int)
go func() { ch <- compute() }() // 启动一个goroutine，算是把结果送进channel
result := <-ch
```

这背后是CSP思想，廉价的有栈携程与M:N调度器，以及channel的实现。取舍是：换来为每件事开一个goroutine的书写顺手，代价是运行时要背一个复杂的角度器。

- **接口是结构化，隐式满足的**。一个类型只要拥有接口满足的方法，就自动满足它，无需implements声明。

```
type Reader interface { Read(p []byte)(int, error)}
// 任何拥有Read([]byte)(int,error)方法的类型，自动就是Reader
```

这就是组合优于继承，结构化优于名义类型的体现。取舍是：换来极松的解耦（小接口遍地适配）， 代价是接口调用时间接的，难以跨接口内联。

- **错误是值，不是异常**。 错误经普通返回值显式传递，显式处理，没有try/catch的隐式跳转。

````
    f, err := os.Open(name)
    if err != nil {
        return fmt.Errorf("open %s: %w",name, err) // 包装上下文，显式上抛
    }
    defer f.Close() // defer把清理写在旁边
    ```
````

error, %w包装，取舍是：换来错误路径处处可见，无处可藏，代码是满屏的if err != nil

- **值语义与少数的核心容器**。Go没有庞大的容器库，及户一切都建立在三样东西上：数组/切片，map,channel.切片是指向数组的一段视图，赋值传的是这个轻量视图，
  而非整份拷贝。

```
    s := []int{1, 2, 3}
    t := append(s, 4)   // 可能与s共享底层数组，也可能另外分配，取决于cap

```

- **显式优于隐式**。没有运算符重载，没有隐式数值转换，未使用的导入于变量直接编译报错。看一行代码，几乎总是能猜出它做什么，这份无魔法是刻意的设计纪律。

## 1.3 顺序进程通讯

Go并发模型的思想源头，是Hoare与1978年在CACM上提出的顺序进程通讯（Communicating Sequential Processes,CSP).这一节从
思想史的角度交代这份血脉，它解释了goroutine与channel为何是今天这个样子。

### 1.3.1 CSP的核心主张

上个世纪70年代，多核处理器还是科研主题，尚未进入普通程序员的视野。彼时协调并发的手段已经不少：信号量（Dijkstra,1965),监控
（Hoare,1974），锁和互斥，消息传递。

CSP的核心是一句反直觉的主张：**进程之间不共享状态，只通过传递消息来协调**。在共享内存的世界里面，多个线程读取同一块内存，靠锁防止
彼此踩踏，这即是危险（数据竞争，死锁），又难以理解。CSP反其道而行：每个顺序进程守护着自己的状态，要写作就发消息，通过一次同步的通信
动作来交换数据与控制权。 Go把这条主张凝练成那句广为人知的格言：不要共享内存的方式通信，而要以通信的方式共享内存。

### 1.3.2 1978年的CSP：按照进程名通信，没有channel

读者若翻到Hoare 1978年的原始论文，会发现一件出乎意料的事情：那门语言没有第一类的channel.通信不是把数据头巾某条匿名管道，而是
直接指名某个进程。两个基本算符号是：

p!value: 向名为p的进程发送一个值；
q?var:从名为q的进程接收一个值，存入var

发送方写下接收方的名字，接收方也写下发送方的名字，只有当双方在对应的语句上会合（rendezvous）时，这次通信才发生，值被复制过去。
两边各自继续。整门语言有由个运算符撑起来：顺序 ; 并行 || 赋值 := 输入 ? 输出 ! 守卫 -> 选择 □ 重复 \* 比如：

```
[west:DISASSEMBLE || X::COPY || east::ASSEMBLE]
```

就启动三个并行进程，进程之间用名字互相寻址。这种暗进程名通信的设计有一个朴素的优点：语言里面不必引入channal这种额外的概念。但
它的代价也很直接，子过程必须知道使用它的过程名字，难以封装成可复用的库；而并行组合`[a::P || b::Q]`是一个参数个数可变的运算。
无法进一步代数化简。Hoare本人在1985年的专著里面就修正了这两处。

把通信实体抽象成一条可独立命名，可作为值传递的channel,时候来才发生的事情：它在1980年代初的occam语言中确立，并由1985年的CSP
专著配上一套修订后的进程代数。Go继承的，正是这条后期的，以channel为中心的脉络，而非1978年的进程名寻址。所以后来当我们在Go里面写
make(chan int),把它存进变量，塞进结构体，甚至从一个channel里面收到另外一个channel时，依据的是occam与1985年专著的传统，不是
那篇萌芽的论文。

### 1.3.3 进程代数的谱系：从CCS到π-演算

CSP不是孤峰。它周围，Robin Milner几乎同时发展出另一支进程代数，CCS(Calculus of Communicating Systems,Milner 1980)。CCS
与CSP把双方在一个动作上同步作为代数原子，并发展出互模拟（bisimulation）这一刻化进程等价工具。

CCS真正与Go血脉想管的一步，是它的后继π-演算。π-演算给进程代数加进了移动性（mobility）：通道的名字本身作为消息在通道上传递。一个进程
把某条通道的名字发给另外一个进程，后者于是获得了在那条通道上通信的能力，通信的拓扑结构因此能在运行时改变。这正是Go里面chan chan T(通道
的通道)所表达的东西，也是channel是第一类值这一设计在理论上的对应物。下面这段把一个通信通道随请求一起发出去就是π-演算移动性最常见的Go
形态。

```
type request struct {
    arg int
    reply chan int
}

func server(reqs <-chan request) {
    for r := range reqs {
        r.reply <- r.arg * r.arg //沿着对方给的通道回送结果
    }
}
```

### 1.3.4 occam的ALT与Go的select

CSP还有一件遗产得单独点出：守卫选择。它源自于Dijkstra的守位指令，到occam里变成了ALT,在Go里面就是select。它要解决的问题是：一个进程
同时面对多路通信，哪一路先就绪就先处理哪一路，而不必预先规定顺序。在1978年的CSP里面，它写作：

```
*[X?V() → val := val+1 □ val > 0; Y?P() → val := val-1]
```

□ 分隔几个守卫分支，每个分支以依次输入为守卫；若多个守卫同时就绪，则随机选择一个执行。这个随机不是偷懒，而是为了提供公平性，避免某一路通信
被长期饿死。Go的select原封不动继承了这条语意：多个case同时就绪时，运行时随机的选择一个。

### 1.3.5 Go的并发原型：用代码说话

谱系讲清楚了，落到Go本身，模型只有两件东西：goroutine(顺序进程)与channel(通信)。一个go关键字发起一个goroutine,一个<-完成一次通行。

最基本的形态是一次发送与一次接收：

```
ch := make(chan int)
go func() { ch <- 42 }() //一个goroutine发送
v := <-ch   // 另外一个goroutine接收得到42
```

channel是否带缓冲，决定了这次通信是同步会合还是异步投递，这正是CSP1978年的两种形态。无缓冲channel是纯粹的rendezvous,发送方会一直
阻塞，直到某个接收方就位，两者在通信点上严格汇合；带缓冲channel则允许发送方在缓冲未满时先走一步，把一次同步松弛成一个有界队列（1978年
的CSP未把带缓冲通信作为原语，Hoare是用一个无缓冲模拟带缓冲来的，以有界队列松弛同步这一概念，正是带缓冲channel的思想先声。

```
unbuffered := make(chan int) // 容量0:发送到阻塞接受就位（会合）
buffered := make(chan int, 4) // 容量4:未满即发送，无需等待接收
```

select让一个goroutine在多路通信间择一而动，并可借default做非阻塞尝试，借time.After做超时：

```
select {
case v := <-in:
    handle(v)
case out <- result:
    //成功发出
case <-time.After(time.Second):
    // 超时退出，避免永久阻塞
}
```

有了这三样，CSP的经典模式就是顺理成章的写法。Hoare 1978年论文里面那个DISASSEMBLE -> COPY -> ASSEMBLE的例子（从80列卡片读入，逐字符流转，再
排成125列打印），本质上是一条流水线（pipeline）：每个进程顺序的做一件小事，用channel把上下游连接起来，数据沿着channel流动。它就是几个goroutine
串成一串。

```
// COPY：把上游字符原样转给下游，读到尽头就关闭下游
func copyStage(west <-chan rune, east chan<- rune ) {
    for c := range west {
        east <- c
    }
    close(east) // 关闭，下游的rang随之结束
}

// 把三段结成流水线：上有关闭逐级传播，整条管线自然结束
func reformat(cardfile <-chan []rune, lines chan<- string) {
    west, east := make(chan rune), make (chan rune)
    go disassemble(cardfile, west)
    go copyStage(west, east)
    assemble(east, lines) // 末端在当前goroutine同步执行
}

```

这里有一个Go化的关键约束：用close表达数据流结束，下游的for range会在channel关闭且取空后自然退出，关闭信号于是沿着流水线逐级传播。
同一个手法另外一面，时用一个专门的done channel来广播取消，一旦关闭，所有监听它的goroutine都会在<-done上理解接触阻塞：

```
func worker(in <-chan int, done <-chan struct{}) {
    for {
        select {
        case  v := <-in:
            process(v)
        case <-done: // 上游关闭done，这里立即返回
            return
        }
    }
}

```

这套以channel流转数据，以close传播信号的写法，是以Go并发代码反复出现的骨架，也是context包取消机制的底层形态。

### 1.3.6 CSP与Actor模型

与CSP同代，却走向另外一条路，是Hewitt等人1973年提出的Actor模型，它在Erlang里面得到了完整的工程化。两者都主张不共享状态，靠消息协作，分别在于消息
传递给谁，何时送达，实体有没有身份。

一句话概括：CSP让你给通信的管道命名，Actor让你给通信的对端命令。Go选择了前者，于是goroutine彼此不知道对方时谁，只共同维持了一条channel;channel
在谁手里，谁就能参与这场通信。Erlang选择了后者，于是每个进程有地址，有mailbox,并在此之上又出了CSP没有对应物的容错体系：进程可以互相链接，监督，一个
奔溃可以让监督者按策略重启它。它两路各有所长，Go没有照搬任何一条到底。

### 1.3.7 Go对CSP的取舍：与这份血脉为何重要

Go没有把CSP当教条，每一处改动都体现它的工程味：

- 不是纯CSP.Go保留了共享内存与锁。它把CSP作为首选而非唯一，该用channel表达流时用channel,该用一把锁保护住一小块状态的时候就用锁。这种不教条，
  正式Go的风格。
- channel是一等公民。可传递，可存储，可经channel发送channel,让通信拓扑能在运行时变化。（即1.3.3的π-演算式移动性）。
- goroutine极廉价。CSP的进程在Go里面时goroutine,起步仅2KB栈，可同时存在百万计，让为每件并发的事情开一个进程，从理论上的优雅变得在实践中可行。
- select即守卫选择。ocdam的ALT在Go里变成了select.

这份CSP的这条血脉，深刻塑造了Go程序的样貌。它激励我们把并发想象成一组各自顺序执行，彼此用channel连接的小进程：数据沿用channel流动，所有权随之
移动，于是同一块数据同一时刻只被一个goroutine持有成了自然结果，竞争与锁的心智负担因此大为减轻。这和Go整体显式，简单的哲学一脉相承，通信是显式的
并发单元是廉价而独立的。理解了这份从1978年的进程名，经由occam与π-演算，到贝尔实验室实验语言的思想血脉，再去读9调度器与10通道与select，就即见树木，
又见森林了。
